# گزارش فاز ۰ — تحلیل خط مبنا و تصمیم‌های اجرایی

**تاریخ:** ۲۰۲۶-۰۸-۱۲

**مخزن:** `pchreza/portal3`

**Commit پایه:** `0d1c08b` — `v2.0.0`

## ۱. وضعیت خط پایه

مخزن موجود یک پورتال مشتریان با PHP خالص، PDO و MySQL است. README آن نصب `install.php`، صفحات `admin/` و `customer/`، قالب‌های مشترک `includes/layout/`، توابع کمکی و Migrationهای نسخه‌بندی‌شده را توضیح می‌دهد. `composer.json` در حال حاضر PHP حداقل ۸.۱، PhpSpreadsheet و PHPUnit/PHPStan را تعریف می‌کند. تست موجود در `tests/Unit/HelpersTest.php` روی نرمال‌سازی مبلغ، تبدیل تاریخ جلالی، Escape HTML و CSRF تمرکز دارد.

اسکیمای موجود شامل `users`, `settings`, `projects`, `products`, `tickets`, `invoices`, `notifications`, `surveys`, `activity_logs` و جداول مرتبط است. این اسکیمای فعلی تک‌مستأجری است و جدول‌های کلینیک، شعبه، بیمار، دندان، نوبت، طرح درمان، کیف پول و جداسازی کلینیکی ندارد.

## ۲. محدودیت محیط توسعه

در محیط sandbox فعلی دستور `php` در PATH وجود ندارد؛ بنابراین اجرای PHPUnit، lint PHP، PHPStan، Composer و اجرای محلی برنامه در خط مبنای فاز ۰ امکان‌پذیر نبود. این موضوع خطای محصول نیست و باید در ابتدای فاز ۱ با نصب PHP 8.2/8.3 و افزونه‌های `mbstring`, `xml`, `zip`, `pdo_mysql` و ابزار Composer برطرف شود. نصب وابستگی‌های پروژه نباید با داده یا اسرار تولیدی انجام شود.

| مورد | مشاهده | اثر |
|---|---|---|
| معماری فعلی | PHP خالص و صفحه‌محور | قابل حفظ است، اما نیاز به مرزبندی ماژولار و سرویس‌های نوع‌دار دارد. |
| داده | پورتال مشتریان تک‌مستأجری | Migration دندانی جدید باید از مدل فعلی جدا و دارای `clinic_id` باشد. |
| نصب | installer موجود | باید برای SaaS، Seed، lock، برند، SA و clinic lifecycle توسعه یابد. |
| Migration | `migrations.php` و `bin/migrate.php` | الگوی موجود قابل استفاده است؛ باید status/lock/backup/rollback عملیاتی تکمیل شود. |
| تست | یک suite کوچک PHPUnit | باید به unit، feature، integration، security و tenant isolation گسترش یابد. |
| RTL | Tailwind local و Vazirmatn در پروژه موجود است | باید با قواعد CSS منطقی، محتوای ترکیبی و چهار breakpoint بازبینی شود. |
| اجرای محلی | PHP در محیط موجود نصب نیست | فاز ۱ باید ابزار اجرا و گزارش baseline را فراهم کند. |

## ۳. تصمیم معماری مهاجرت

تصمیم فاز ۰، بازنویسی مخرب و حذف جدول‌های پورتال موجود نیست. محصول از پایهٔ PHP خالص موجود استفاده می‌کند، اما حوزهٔ دندان‌پزشکی در Migrationها، نام‌گذاری، Repositoryها و مسیرهای مجزای خود ساخته می‌شود. اجزای مفید موجود مانند `e()`, CSRF، نرمال‌سازی مبلغ، تبدیل تاریخ، قالب محلی و چارچوب Migration پس از بازبینی حفظ یا استخراج می‌شوند. کدهای Legacy مستقیماً به دامنهٔ جدید وارد نمی‌شوند مگر آن‌که تست و قرارداد رفتاری داشته باشند.

در فاز ۱ ساختار پیشنهادی زیر ایجاد یا تثبیت می‌شود:

```text

├── Domain/
│   ├── Auth/
│   ├── Tenancy/
│   ├── Clinic/
│   ├── Patient/
│   ├── Dental/

│   ├── Billing/
│   ├── Notification/
│   └── Operations/

    ├── Http/
    ├── Views/
    └── Support/
```

این ساختار در ابتدا می‌تواند در کنار مسیرهای Legacy کار کند و تا تکمیل ماژول‌ها از شکستن ناگهانی پورتال فعلی جلوگیری نماید. هر مسیر جدید باید از Context مستأجر، Permission Service، Validator و Audit Service استفاده کند.

## ۴. ریسک‌های مسدودکنندهٔ فاز ۱

| ریسک | وضعیت | تصمیم |
|---|---|---|
| نبود PHP/Composer در sandbox | فعال | در فاز ۱ ابزار توسعه نصب و نسخه‌ها ثبت شود؛ بدون آن تست سبز ادعا نشود. |
| نبود دیتابیس MySQL محلی | نامشخص | تست‌های واحد مستقل باشند؛ برای integration یک MySQL ایزوله یا محیط تست فراهم شود. |
| تفاوت cPanel و sandbox | ذاتی | installer و upgrade باید با قابلیت‌های استاندارد PHP و بدون SSH طراحی و روی محیط شبیه‌سازی‌شده آزمایش شوند. |
| ابهام انتخاب framework | حل‌شده | محصول PHP خالص باقی می‌ماند؛ ساختار ماژولار و وابستگی حداقلی بر پایهٔ کد فعلی ادامه می‌یابد و framework سنگین بدون تأیید جدید وارد نمی‌شود. |
| رشد تا دو میلیون بیمار | کنترل‌پذیر | از ابتدا index، pagination، archive و tenant scope اجباری است؛ sharding فعلاً خارج از محدوده است. |
